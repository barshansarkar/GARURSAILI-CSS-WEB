Guide 01 · ~5 min read

With Next.js

Garur emits a plain CSS file, so integration is a build-time concern. You run Garur once before next build, commit the output path to your root layout, and let Next.js handle the rest. There is no webpack loader, no PostCSS plugin, and no runtime in the browser.

Project layout

A typical Next.js project using Garur has three additional files at the root: a config, a build output folder, and one import statement in the layout. Everything else stays as-is.

project tree 
my-app/
├── app/
│   ├── layout.tsx          // imports garur.css
│   └── page.tsx
├── build/
│   └── garur.css           // generated — do not edit
├── garur.config.js         // optional
├── next.config.mjs
└── package.json

Wire it into the build

The cleanest approach is a prebuild script in package.json. NPM runs prebuild automatically before build, so Garur always sees the latest source.

package.json 
{
  "scripts": {
    "dev": "next dev",
    "prebuild": "garur ssc ./app ./components --minify",
    "build": "next build",
    "watch:css": "garur watch"
  }
}

Import in the root layout

In the App Router, import the generated stylesheet in app/layout.tsx. Next.js will inline it into the build automatically.

app/layout.tsx 
import '../build/garur.css';
import type { Metadata } from 'next';

export const metadata: Metadata = {
  title: 'My App',
};

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body className="bg-white dark:bg-[#0a0a0a]">
        {children}
      </body>
    </html>
  );
}

Dev workflow

During development, run Garur in watch mode alongside next dev. Garur watches your source files and rebuilds in ~3 ms on each save, so the CSS is always current by the time Next's HMR runs.

terminal · two panes 
# pane 1
$ npm run watch:css

# pane 2
$ npm run dev
Tip — run both in one command. Use npm-run-all or concurrently: concurrently "garur watch" "next dev".

Pages Router

If you're on the Pages Router, import the stylesheet in pages/_app.tsx instead. Everything else stays the same.

pages/_app.tsx 
import '../build/garur.css';
import type { AppProps } from 'next/app';

export default function App({ Component, pageProps }: AppProps) {
  return <Component {...pageProps} />;
}

Common pitfalls

Symptom Fix
Styles missing on first load Garur hasn't run yet. Add prebuild script.
Stale CSS after class change Restart garur watch — it caches by file hash.
Turbopack complaining about imports Point the import at build/garur.css, not a folder.
Deployed build missing classes Check that build/ is not in .gitignore.
Guide 02 · ~4 min read

With Vite

Vite does not need a plugin to work with Garur. Because Garur produces a plain CSS file, you can import it directly in your entry point and let Vite handle bundling, HMR, and code-splitting.

Entry import

Import the generated CSS from src/main.ts. Vite treats it as a first-class module — no link tag needed.

src/main.ts 
import '../build/garur.css';
import { createApp } from 'vue';
import App from './App.vue';

createApp(App).mount('#app');

Dev workflow

Run Garur and Vite as parallel processes. Vite's HMR is CSS-agnostic — when Garur rewrites build/garur.css, Vite picks up the change within a frame.

package.json 
{
  "scripts": {
    "dev": "concurrently \"garur watch\" \"vite\"",
    "prebuild": "garur ssc ./src --minify",
    "build": "vite build"
  }
}
Why no plugin? A Vite plugin would need to rebuild the CSS on every file change — but Garur already does that in watch mode, faster than a plugin could. Two processes, one source of truth.

Production build

The prebuild script runs before vite build. Garur emits both the unminified and minified files; Vite imports the unminified one and minifies it again as part of its pipeline. To avoid double-minification, point the import at build/garur.css and let Vite do the final pass.

vite.config.ts 
import { defineConfig } from 'vite';

export default defineConfig({
  css: {
    devSourcemap: true,
  },
  build: {
    cssMinify: 'lightningcss',
  },
});

Turbopack and Rolldown

If you're on Vite's Rolldown beta or using vite-plugin-wasm, everything still works — Garur's output is plain CSS and does not require any bundler-specific integration.

Guide 03 · ~6 min read

Custom themes

Garur exposes everything a primitive needs as a CSS variable. That means theming does not require a rebuild — you can swap a brand color, change the base radius, or add a new semantic palette entirely at runtime by overriding variables on :root.

Three layers of theming

1 · Runtime tokens

Override --garur-* variables on :root. Affects every primitive instantly — no rebuild.

2 · Config palette

Add brand families to garur.config.js. Generates new utility classes like bg-brand-500 — requires a rebuild.

3 · Semantic colors

Opt-in layer for bg-primary, text-success, and other role-based utilities. Rebuild required.

Runtime tokens

Every primitive in Garur reads from a design token. To retheme, override the token — no rebuild, no class changes. This works because primitives never hardcode colors, radii, or shadows.

globals.css 
:root {
  --garur-primary: #c2410c;
  --garur-radius: 0.25rem;
  --garur-surface: #fefefe;
  --garur-shadow-md: 0 2px 4px rgba(0,0,0,0.06);
}

.dark {
  --garur-surface: #111111;
  --garur-primary: #fb923c;
}

The primitives that read these tokens include card, btn, input, badge, alert, toast, modal, and every avatar / divider variant.

Adding a brand palette

For brand colors you want to use as utility classes (bg-brand-500, text-brand-600), define them in the config. Garur generates the full shade ramp and every variant automatically.

garur.config.js 
export default {
  palette: {
    brand: {
      50:  '#fff7ed',
      100: '#ffedd5',
      200: '#fed7aa',
      300: '#fdba74',
      400: '#fb923c',
      500: '#f97316',
      600: '#ea580c',
      700: '#c2410c',
      800: '#9a3412',
      900: '#7c2d12',
      950: '#431407',
    },
  },
};

After a rebuild, every color utility has a new variant: bg-brand-500, text-brand-600, border-brand-300, ring-brand-400, fill-brand-500, from-brand-400, and the full opacity ramp (bg-brand-500/50, etc.).

Semantic colors

Semantic colors are an opt-in layer that maps role names — primary, success, danger, and so on — to a color. They are off by default because most projects prefer literal color names. Enable them when your design system uses role-based tokens.

garur.config.js 
export default {
  semanticColors: true,
  semanticOverrides: {
    primary:   '#c2410c',
    success:   '#16a34a',
    danger:    '#dc2626',
    'warning-fg': '#422006',
  },
};

Enabling this generates bg-primary, bg-primary-hover, bg-primary-subtle, text-primary, border-primary, ring-primary, and equivalents for each of the eight roles. The generated utilities reference CSS variables, so you can still override them at runtime — --garur-primary wins over the config value.

Which should I pick? Use literal colors (bg-iris-500) when your design language has a fixed palette. Use semantic colors when the same UI element needs to change color across themes without a class change.

Dark mode

Dark mode is configured with the darkMode key. The default is 'class' — the dark: variant fires when an ancestor has class dark. Set it to 'media' to follow the OS preference instead.

garur.config.js 
export default {
  darkMode: 'class', // or 'media'
};
Guide 04 · ~5 min read

Component patterns

A long class string in JSX is fine once. Repeated twenty times across a codebase, it becomes a maintenance problem. Garur gives you three ways to solve this, in increasing order of structure.

Pattern 1 — Constant strings

The simplest pattern: extract the class string into a constant. No new syntax, no build step, works in every framework. If the string never changes based on props, this is enough.

Button.tsx 
const BTN = 'inline-flex items-center gap-2 px-4 py-2 rounded-md font-medium text-sm transition-colors';
const PRIMARY = 'bg-graphite-950 text-white hover:bg-graphite-800 dark:bg-white dark:text-black';
const GHOST = 'text-graphite-700 hover:bg-graphite-100 dark:text-graphite-300';

export function Button({ variant = 'primary', children }) {
  const style = variant === 'primary' ? PRIMARY : GHOST;
  return <button className={`${BTN} ${style}`}>{children}</button>;
}

Pattern 2 — Garur primitives

For UI that maps to an existing primitive, prefer the primitive over a raw utility string. The primitive reads from --garur-* tokens, which means theming works automatically — no need to touch the component when the theme changes.

Button.tsx 
export function Button({ variant = 'primary', children }) {
  const cls = {
    primary: 'btn btn-primary',
    ghost:   'btn btn-ghost',
    danger:  'btn btn-danger',
  }[variant];

  return <button className={cls}>{children}</button>;
}

The advantage over Pattern 1: when you retheme — say you change --garur-primary to orange — every button updates without a rebuild or a source change. The class string never references a literal color.

Pattern 3 — @apply in CSS

When a class string would be reused in HTML you don't control — markdown, CMS content, third-party embeds — extract it into a named class in your stylesheet. Garur expands @apply at build time and folds it into the output.

components.css 
.callout {
  @apply p-4 rounded-lg border border-graphite-200 dark:border-white/10;
}

.callout-info {
  @apply bg-sky-50 border-sky-200 text-sky-900;
}

.callout-info .callout-title {
  @apply font-medium mb-1;
}

@apply also accepts variants: @apply hover:rise focus-visible:ring-2 md:grid-3. Variants compile into the nested selector form, so the resulting CSS matches what you'd write by hand.

Don't over-abstract. If a string is used once, keep it inline. Extracting it into a named class adds indirection with no payoff. The three patterns above are ordered by when they start paying off — use each only when the case warrants.
Guide 05 · ~7 min read

Migrating from Tailwind

Garur's utility layer is deliberately familiar to Tailwind users. Most atomic utilities carry the same name, and the variant syntax is identical. The differences are in the palette, the primitive layer, and how the build is wired.

What stays the same

Category Compatible
Spacing scalep-4 · m-2 · gap-3 — identical values
Layout utilitiesflex · grid-cols-3 · justify-between
Sizingw-full · max-w-2xl · min-h-screen
Typographytext-lg · font-bold · leading-relaxed
Variantshover: · md: · dark: · group-hover:
Arbitrary valuesw-[42rem] · bg-[#0a0a0a]

What changes

Color palette

Garur ships its own 31-family palette. Slate, zinc, and neutral are replaced by void, graphite, and ash. Brand colors are named after materials — iris, plum, jade — rather than abstract labels.

Default breakpoints

The sm · md · lg · xl · 2xl breakpoints carry the same widths as Tailwind, so no source changes are needed.

Primitive layer

Tailwind has no primitive layer. Garur adds classes like card, btn, navbar, modal, and alert that replace common utility strings. Use them or ignore them — both work.

Build tool

No PostCSS plugin. No tailwind.config.js. Replace the Tailwind CLI with garur ssc ./src and remove the PostCSS entry from your bundler config.

Class name mapping

Most class names carry over unchanged. Only the palette names differ. The table below maps the most common Tailwind palette classes to their Garur equivalent.

Tailwind Garur Notes
slate-*void-*cool-tinted neutral
zinc-*graphite-*true neutral
neutral-*graphite-*true neutral
stone-*smoke-*warm neutral
blue-*azure-*vivid blue
sky-*sky-*unchanged
indigo-*cobalt-*deeper blue
violet-*iris-*blue-purple
purple-*violet-*classic violet
fuchsia-*orchid-*pink-purple
pink-*rose-*classic rose
red-*ruby-*rich red
orange-*ember-*deep orange
amber-*honey-*amber gold
yellow-*sunbeam-*bright yellow
green-*forest-*deep green
emerald-*jade-*blue-green
teal-*teal-*unchanged

Automated find and replace

For projects using a small palette of Tailwind colors, a targeted sed pass migrates most of the source. The regex below matches class attributes and replaces the Tailwind family prefix with the Garur equivalent.

terminal 
# macOS + GNU sed
$ find ./src -type f \( -name "*.tsx" -o -name "*.jsx" \) -print0 \
  | xargs -0 sed -i '' \
    -e 's/\\bslate-/void-/g' \
    -e 's/\\bzinc-/graphite-/g' \
    -e 's/\\bneutral-/graphite-/g' \
    -e 's/\\bstone-/smoke-/g' \
    -e 's/\\bgray-/ash-/g' \
    -e 's/\\bblue-/azure-/g' \
    -e 's/\\bindigo-/cobalt-/g' \
    -e 's/\\bviolet-/iris-/g' \
    -e 's/\\bpurple-/violet-/g' \
    -e 's/\\bfuchsia-/orchid-/g' \
    -e 's/\\bred-/ruby-/g' \
    -e 's/\\borange-/ember-/g' \
    -e 's/\\bamber-/honey-/g' \
    -e 's/\\byellow-/sunbeam-/g' \
    -e 's/\\bgreen-/forest-/g' \
    -e 's/\\bemerald-/jade-/g' \
    -e 's/\\bcyan-/aqua-/g'
Review every change. A blind find/replace will also hit strings, comments, and API responses. Always diff the result and run the site locally before committing.

Keep Tailwind alongside

For large codebases, migrating incrementally is faster than a big-bang rewrite. Run both engines side by side: Tailwind for existing components, Garur for new ones. Both emit plain CSS, so they can coexist in the same project.

package.json 
{
  "scripts": {
    "prebuild": "garur ssc ./app/new --minify",
    "build": "next build"
  }
}
Guide 06 · ~6 min read

Performance tuning

Garur's compile is fast by default. If your build is slower than expected, the cause is almost always one of: overly broad content globs, a missing persistent cache in CI, or a large number of uncached files. This guide walks through each in turn.

Measure first

Before tuning, take a baseline. The garur benchmark command runs the compiler N times against your project and prints average, min, and max latency alongside cache hit rate.

terminal 
$ npx garur benchmark --runs 10

  Files:        247
  Classes:      1,842
  Average:      28ms
  Min:          24ms
  Max:          41ms

  Cache performance:
    build  ████████████████████ 99.4%  1,832h / 10m

Content globs

Garur walks the file tree looking for class names. By default it scans the entire project (except common ignore folders). Narrowing the content globs to only the directories that actually contain UI code cuts scan time substantially on monorepos.

garur.config.js 
export default {
  content: [
    './app/**/*.{tsx,jsx}',
    './components/**/*.{tsx,jsx}',
    './content/**/*.mdx',
  ],
  ignore: [
    '**/*.test.*',
    '**/*.stories.*',
    './app/api/**',
  ],
};

The most common cause of slow scans is a glob that accidentally matches node_modules, dist, or .next. These directories are excluded by the default ignore list, but if you override content without preserving the ignore list, they may be included.

Persistent cache

Garur keeps two caches: an in-process build cache (keyed by class name) and a cross-process file cache (keyed by content hash). The first is discarded when the process exits; the second is written to .garur-cache.bin and read on the next run.

In CI, cache .garur-cache.bin between runs. A warm cache cuts cold-start compile time in half.

.github/workflows/build.yml 
- uses: actions/cache@v4
  with:
    path: .garur-cache.bin
    key: garur-${{ hashFiles('app/**', 'components/**') }}
    restore-keys: garur-

- run: npx garur ssc ./app ./components --minify

Watch vs one-shot

Command Best for Latency
garur ssc CI, one-off builds ~30ms cold · ~5ms warm
garur watch Local development ~3ms per rebuild
garur build Pre-commit hooks, scripts ~30ms cold

Large class counts

Above roughly 20,000 unique classes, build time is bounded by the size of the generated stylesheet, not by the compiler. At this scale the CSS file itself becomes the bottleneck. Two strategies help:

Split per route

Run Garur once per top-level route with its own content globs. Each route ships only the classes it needs.

Prune aggressively

Add test files, stories, and generated code to ignore. Garur compiles them the same as production files.

Diagnostics

Set GARUR_DEBUG=1 to see the exact file list, platform key, and native binary path. This is the fastest way to diagnose "why is my build slow" — the output tells you whether Garur is scanning more files than expected.

terminal 
$ GARUR_DEBUG=1 npx garur ssc ./src

[garur] Platform: darwin-arm64
[garur] Binary names: garur_core.darwin-arm64.node, index.cjs
[garur] Native candidates (12):
   /Users/me/project/garur_core.darwin-arm64.node
   /Users/me/project/node_modules/garursaili-css/...
[garur] Found 247 files
[garur] Found 1,842 unique classes
