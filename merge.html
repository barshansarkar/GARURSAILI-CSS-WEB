Docs / Introduction

Introduction

Garur is a semantic hybrid CSS engine. It fuses three layers — intent, primitive, and utility — into a single native Rust binary that compiles at the speed of disk I/O.

Stable · v0.2.0
· Last updated October 2026

What is Garur?

Garur is a compiler. You write class names in your markup, point Garur at your source files, and it emits exactly the CSS you use — nothing more, nothing less. There is no runtime, no plugin chain, and no JavaScript shipped to the browser.

What makes Garur different is that its vocabulary spans three layers of abstraction. You can write mid to mean "center on both axes" without remembering whether that's flex or grid. You can write card-glass and get a complete translucent surface with border, radius, shadow, and backdrop blur. You can also write raw utilities like p-4 and bg-iris-500 when you need precise control.

All three coexist. Compose them together. The engine handles the rest.

Note

Garur is a build-time tool. It has zero effect on your application's runtime bundle. The output is a plain CSS file — no CSS-in-JS, no injected style tags, no runtime style computation.

Installation

Garur is distributed as a prebuilt native binary via N-API. Installation does not require a Rust toolchain, a build step, or any native compilation on your machine.

Install the package

terminal 
$ npm install garur

Garur works with npm, pnpm, Yarn, and Bun without configuration. The package ships precompiled binaries for macOS (x64, arm64), Linux (x64, arm64), and Windows (x64).

Verify installation

terminal 
$ npx garur --version
garur/0.2.0
native/ferrous-engine
targets/2023

Quick start

The fastest way to see Garur work is with the built-in ssc command. It scans your source files, extracts classes, and emits a single stylesheet in one pass.

1. Scan and build

terminal 
$ npx garur ssc ./src
✓ Scanned 124 files
✓ Extracted 842 unique classes
✓ Built in 28ms
→ ./build/garur.css · 14.2 KB

2. Link the stylesheet

index.html 
<link rel="stylesheet" href="./build/garur.css" />

3. Write classes

page.html 
<div class="mid stack-4 p-8">
  <h1 class="text-3xl font-bold">Hello</h1>
  <button class="btn btn-primary">Get started</button>
</div>

Three layers

Garur's vocabulary is organized into three layers. Each layer has a distinct purpose. Understanding them helps you decide which class to reach for when.

1

Intent layer

Describes what you mean using vocabulary that maps to your mental model. mid means "centered both axes." apart-mid means "space-between, aligned." rise means "elevated with a shadow."

2

Primitive layer

Component-level shorthands powered by runtime tokens. card gives you a complete surface with border, radius, padding, and shadow. btn gives you a button skeleton. Every token is a CSS variable, so theming works at runtime.

3

Utility layer

Atomic utilities with a familiar syntax — p-4, bg-iris-500, grid-cols-3, hover:rise. Full variant support, arbitrary values, and opacity modifiers.

Layers compose freely. There is no rule preventing you from mixing a primitive with utilities, or using an intent alongside raw atomic classes. Utilities win the cascade where they overlap, so card p-2 overrides the card's default padding.

Intent layer

Intents replace combinations of flex, gap, justify, and align declarations with a single class. They read the way you would describe the layout to another engineer.

Primitive layer

Primitives are complete component shorthands. Every primitive reads its values from --garur-* CSS variables, which means you can retheme the entire system at runtime by overriding those variables on :root.

Variants

Any utility, primitive, or intent can be prefixed with a variant. Prefixes stack from left to right — md:dark:hover:bg-iris-500 applies on medium screens, in dark mode, on hover.

Variant Applies when
hover:Pointer is over the element
focus-visible:Element is keyboard-focused
active:Element is being pressed
disabled:Element has [disabled]
dark:Dark mode is active
md: · lg: · xl:Viewport meets breakpoint
group-hover:Parent with .group is hovered
has-[:checked]:Element matches :has() selector
motion-safe:Reduced-motion is not preferred

CLI reference

Garur ships a single CLI binary. Every command accepts a positional path or uses the current directory by default.

garur build — compile stylesheet from config 
$ garur build [--watch] [--minify] [--out ./build/garur.css]
garur ssc — one-shot scan, extract, build 
$ garur ssc ./src [--preflight] [--minify]
garur init — scaffold a config file 
$ garur init [--force]

Configuration

Garur works with zero configuration. When you need to customize, create garur.config.js at the project root. Only the keys you provide are overridden — the rest inherit sensible defaults.

garur.config.js 
export default {
  content: ['./src/**/*.{html,tsx,jsx,vue}'],
  output: './build/garur.css',
  darkMode: 'class',
  breakpoints: {
    sm: '640px',
    md: '768px',
    lg: '1024px',
    xl: '1280px',
  },
  palette: {
    brand: {
      50:  '#f5f3ff',
      500: '#8657f7',
      900: '#2a0e53',
    },
  },
  semanticColors: true,
};

Semantic colors

Semantic colors map role names to colors. Instead of bg-ruby-600 you write bg-danger. The utility resolves at runtime through a CSS variable, which means the same class changes appearance when you swap themes.

Opt-in. Semantic colors are off by default. Enable them in garur.config.js with semanticColors: true.

Easy mode

Three shorthand forms reduce typing on common cases. They resolve at build time to the same CSS the explicit form would produce.

bg-iris → bg-iris-500

Omitting the shade resolves to 500.

bg-iris-6 → bg-iris-600

Single digit expands to the hundreds.

bg-iris-95 → bg-iris-950

Special case: 95 → 950.

Docs / Guides

Guides

Practical walkthroughs for integrating Garur with your framework, theming it to match your brand, and migrating existing codebases. Each guide is self-contained.

Guide 01 · ~5 min read

With Next.js

Garur emits a plain CSS file, so integration is a build-time concern. You run Garur once before next build, commit the output path to your root layout, and let Next.js handle the rest.

Project layout

project tree 
my-app/
├── app/
│   ├── layout.tsx          // imports garur.css
│   └── page.tsx
├── build/
│   └── garur.css           // generated
├── garur.config.js
└── package.json

Wire it into the build

package.json 
{
  "scripts": {
    "dev": "next dev",
    "prebuild": "garur ssc ./app ./components --minify",
    "build": "next build",
    "watch:css": "garur watch"
  }
}

Import in the root layout

app/layout.tsx 
import '../build/garur.css';

export default function RootLayout({ children }) {
  return (
    <html lang="en">
      <body className="bg-white dark:bg-[#0a0a0a]">
        {children}
      </body>
    </html>
  );
}

Common pitfalls

Symptom Fix
Styles missing on first loadGarur hasn't run yet. Add prebuild script.
Stale CSS after class changeRestart garur watch.
Deployed build missing classesCheck build/ is not in .gitignore.
Guide 02 · ~4 min read

With Vite

Vite does not need a plugin to work with Garur. Import the generated CSS from your entry point and let Vite handle bundling, HMR, and code-splitting.

Entry import

src/main.ts 
import '../build/garur.css';
import { createApp } from 'vue';

createApp(App).mount('#app');

Dev workflow

package.json 
{
  "scripts": {
    "dev": "concurrently \"garur watch\" \"vite\"",
    "prebuild": "garur ssc ./src --minify",
    "build": "vite build"
  }
}
Why no plugin? Garur already rebuilds in watch mode, faster than a plugin could. Two processes, one source of truth.
Guide 03 · ~6 min read

Custom themes

Garur exposes everything a primitive needs as a CSS variable. Theming does not require a rebuild — swap a brand color, change the base radius, or add a new semantic palette at runtime.

Runtime tokens

globals.css 
:root {
  --garur-primary: #c2410c;
  --garur-radius: 0.25rem;
  --garur-surface: #fefefe;
}

.dark {
  --garur-surface: #111111;
  --garur-primary: #fb923c;
}

Adding a brand palette

garur.config.js 
export default {
  palette: {
    brand: {
      50:  '#fff7ed',
      500: '#f97316',
      900: '#7c2d12',
    },
  },
};

Semantic colors

garur.config.js 
export default {
  semanticColors: true,
  semanticOverrides: {
    primary: '#c2410c',
    success: '#16a34a',
  },
};
Guide 04 · ~5 min read

Component patterns

A long class string in JSX is fine once. Repeated twenty times, it becomes a maintenance problem. Garur gives you three ways to solve this.

Pattern 1 — Constant strings

Button.tsx 
const BTN = 'inline-flex items-center gap-2 px-4 py-2 rounded-md';
const PRIMARY = 'bg-graphite-950 text-white';

export function Button({ variant, children }) {
  const style = variant === 'primary' ? PRIMARY : '';
  return <button className={`${BTN} ${style}`}>{children}</button>;
}

Pattern 2 — Garur primitives

Button.tsx 
export function Button({ variant = 'primary', children }) {
  const cls = {
    primary: 'btn btn-primary',
    ghost:   'btn btn-ghost',
    danger:  'btn btn-danger',
  }[variant];

  return <button className={cls}>{children}</button>;
}

Pattern 3 — @apply

components.css 
.callout {
  @apply p-4 rounded-lg border border-graphite-200 dark:border-white/10;
}

.callout-info {
  @apply bg-sky-50 border-sky-200 text-sky-900;
}

Guide 06 · ~6 min read

Performance tuning

Garur's compile is fast by default. If your build is slower than expected, the cause is almost always one of: overly broad content globs, a missing persistent cache in CI, or a large number of uncached files.

Measure first

terminal 
$ npx garur benchmark --runs 10

  Files:        247
  Classes:      1,842
  Average:      28ms
  Cache:        99.4%

Persistent cache in CI

.github/workflows/build.yml 
- uses: actions/cache@v4
  with:
    path: .garur-cache.bin
    key: garur-${{ hashFiles('app/**') }}

- run: npx garur ssc ./app --minify
